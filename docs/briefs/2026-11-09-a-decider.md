### Le board « ne fonctionne toujours pas »

- La cause était propre à l'appli de bureau. Un board tourne dans un cadre
  isolé. Ce cadre héritait de la politique de sécurité de la fenêtre Tauri,
  qui interdit le JavaScript écrit dans la page. Le script du board ne
  tournait donc jamais : les chiffres restaient à « … », et le cadre intégré
  restait tout petit, faute de contenu.
- Correctif : dans l'appli de bureau, le cadre est une vraie page, servie par
  l'appli avec sa propre politique. Elle autorise le script du board, et
  aucun accès au réseau. J'ai vérifié le principe dans Chromium. Je n'ai pas
  pu lancer l'appli Windows ici.
- **À tester** : nouvelle version Windows (Actions GitHub), ouvrir
  « Tableau de bord.board » dans « Vault formats ».

### Tableaux

- Note Markdown : « + Nouvelle ligne » sous le tableau, au survol.
- Base : « + Nouvelle page » sous la dernière ligne.
- Fichier `.table` : un bouton sous la grille. Flèche bas sur la dernière
  ligne, ou Tab sur la dernière case, ajoutent aussi une ligne.
- Un `.table` intégré dans une note prend la hauteur de ses lignes, jusqu'à
  560 px (avant : 260 px fixes).
- L'aperçu d'un lien survolé passe à 720 × 520 px au plus.

### Nature des documents (point 8)

- Un document CRDT autre que le Markdown (`.wtf`, carte mentale, Excalidraw,
  `.tex`…) porte sa nature dans le répertoire du vault. Elle est aussi
  écrite dans `.savoire/documents.json` sur le disque.
- Un membre qui n'a pas le plugin relit donc le document correctement. Avant,
  il le lisait comme vide.
- Les documents anciens reçoivent leur nature dès qu'un membre qui a le
  plugin ouvre le vault. Un lecteur seul n'écrit rien.
- Seule la nature « CRDT » est enregistrée : un instantané se lit déjà comme
  tel sans plugin.

### Import Notion (point 3)

- Bouton « Importer » sous la liste des vaults. On choisit l'archive `.zip`
  exportée par Notion (format « Markdown & CSV »).
- L'archive devient un **nouveau vault**. Sur le serveur, ou dans un dossier du
  poste avec l'appli de bureau.
- Les identifiants de Notion disparaissent des noms. Les pages homonymes
  deviennent « Nom » et « Nom (2) ».
- Une base Notion devient une base Savoire. Ses lignes sont des notes, et
  leurs valeurs vont dans le frontmatter (nombres, cases, dates, choix
  multiples).
- Les liens entre pages deviennent des liens `[[...]]`, et les images des
  `![[...]]`.

### Révision (point 5)

- Sélection, puis « Suggérer une modification » dans la bulle : on écrit le
  texte proposé. Les autres voient le passage barré et la proposition.
- **Accepter** remplace le passage dans la note. C'est refusé si le passage
  a changé entre-temps. **Refuser** ne touche pas la note.
- « Commenter » vise maintenant le passage sélectionné, plus la note entière.
- Les passages en discussion sont surlignés dans l'éditeur. Un clic sur la
  citation, dans le panneau, y mène.
- Le passage suit les modifications des autres : il est accroché au CRDT, pas
  à une position fixe.

### Plugin LaTeX

- À installer depuis le store (plugin de la communauté). Type `.tex`.
- Le source à gauche, l'aperçu à droite, mis à jour à chaque frappe.
- Plusieurs personnes écrivent en même temps. Vérifié avec deux navigateurs
  qui tapent ensemble : les deux textes sont identiques.
- L'aperçu gère les sections numérotées, le titre, les listes, les tableaux,
  les figures, les théorèmes, les notes et les renvois. Les formules sont
  affichées en MathML, par le navigateur lui-même : aucune dépendance.
- « Imprimer / PDF » imprime l'aperçu seul.
- Ce n'est pas une compilation LaTeX : voir Q26.

### Bibliothèques communes entre plugins

- Un plugin venu d'ailleurs que le dépôt n'embarque plus sa copie de React ou
  de CodeMirror. Il les obtient par `require('react')`, dans la version de
  Savoire, comme les plugins d'Obsidian.
- La liste est fermée. Yjs n'y est pas : un plugin passe par l'API CRDT.
- Une bibliothèque hors liste est refusée, avec un message clair.
- Doc : `docs/Architecture/plugin-shared-libraries.md`.

### Connexion par Google, GitHub ou Microsoft

- Il suffit de remplir `GOOGLE_CLIENT_ID` et `GOOGLE_CLIENT_SECRET` dans
  `.env` (pareil pour `GITHUB_…` et `MICROSOFT_…`). Au redémarrage, le bouton
  apparaît sur la page de connexion.
- Vérifié sur le Zitadel de dev avec de faux identifiants, puis retiré.
- **Il te reste** à créer l'appli chez Google (5 minutes), avec l'adresse de
  retour `https://<ton domaine d'auth>/idps/callback`. Marche à suivre dans
  `SELF_HOSTING.md`.

## 3. IA : clés, plugins, connexions HTTP et MCP (proposition)

Rien n'est codé. Voici ce que je propose, en deux parties.

### Partie 1 — Brancher une IA dans Savoire

**Un fournisseur d'IA est un plugin.** L'API des plugins gagne
`api.ai.registerProvider({ id, nom, modèles, répondre(requête) })`.

- Un premier plugin « Compatible OpenAI » couvre déjà OpenAI, Mistral,
  OpenRouter, Ollama et LM Studio (même format d'appel).
- Puis un plugin Anthropic (Claude), dont le format est différent.

**Les clés API.** C'est la décision principale (Q6).

| Option | Où vit la clé | Pour |
|---|---|---|
| A. Clé personnelle | Sur le poste : coffre du système dans l'appli de bureau, navigateur sinon | Chacun paie son IA |
| B. Clé du vault ou de l'organisation | Sur le serveur, chiffrée. Les appels passent par un relais du serveur | La clé n'arrive jamais chez les membres ; quotas par membre |
| C. Les deux | A et B | Recommandé |

**Un agent = un fournisseur + un modèle + des consignes + un mode.** Les modes
existent déjà : lecture, relecture, rédaction, bornés par les droits de la
personne. Les outils de l'agent sont ceux qui existent : lire une note,
chercher, interroger une base, commenter, suggérer.

**D'où partent les appels ?**

- Appli de bureau : depuis Rust. Pas de blocage par le navigateur.
- Navigateur, clé personnelle : en direct. Anthropic l'autorise avec un
  en-tête ; OpenAI à vérifier.
- Clé d'organisation : toujours par le relais du serveur.

### Partie 2 — Savoire utilisable depuis ChatGPT, Claude, etc.

1. **API HTTP publique** avec des jetons personnels révocables, limités à
   certains vaults et à un mode (lecture, relecture, rédaction). Elle est
   décrite en OpenAPI, ce qui suffit pour les « Actions » d'un GPT, n8n ou
   Zapier.
2. **Serveur MCP distant** sur le backend (`/mcp`, transport HTTP).
   - Outils : chercher, lire une note, lister les vaults, interroger une
     base, créer une note, ajouter à une note, commenter, suggérer.
   - ChatGPT et Claude savent tous deux se brancher sur un serveur MCP distant.
   - Connexion par OAuth, via Zitadel. L'enregistrement automatique des
     clients, que demande MCP, est à vérifier chez Zitadel. Sinon, jetons
     personnels.
3. **Serveur MCP local** dans l'appli de bureau, pour Claude Desktop et
   d'autres outils sur le même poste. C'est le seul moyen pour un vault
   chiffré de bout en bout : le serveur ne peut pas le lire.

Une IA externe agit toujours **au nom de la personne**, avec l'attribution
« agent, pour Jean », comme les agents actuels.

**Ordre proposé :** contrat fournisseur et plugin compatible OpenAI, puis les
clés, puis l'agent avec IA, puis l'API HTTP, puis le MCP distant, puis le MCP
local.

## 4. Store de plugins avec un vrai site

Je propose un **projet séparé** (ta décision du 07/10) : un petit site et une
API.

- **Catalogue** : recherche, catégories, tri (populaires, récents, mieux notés).
- **Page d'un plugin** : description, captures, versions, droits demandés
  (affichés clairement), compatibilité, licence, lien vers le code.
- **Avis** : une note de 1 à 5 et un texte, par compte Zitadel (le même compte
  que Savoire). Un avis par personne et par version majeure. L'éditeur peut
  répondre.
- **Publier** : un compte éditeur. Deux modèles possibles (Q12) :
  - comme Obsidian, une « release » GitHub (manifest + paquet) ;
  - un envoi direct sur le site.
- **Contrôles automatiques** à chaque version : manifeste valide, droits
  déclarés, taille, licence, bibliothèques communes seulement, analyse

- **Signature** des paquets. L'appli vérifie avant d'installer.
- **Dans l'appli** : l'onglet Plugins interroge l'API du store. Le store en
  dur reste pour les plugins core.
- **Technique** : la même pile que Savoire (ASP.NET, PostgreSQL, Zitadel). Le
  site peut être statique, regénéré à chaque publication, et l'API petite.

## 5. Partage public, comme Notion et Obsidian Publish

**Aujourd'hui** : un lien de partage `/share/…` ouvre l'appli complète, en
lecture ou en écriture. C'est lourd, mal référencé, et pas fait pour le grand
public.

**Proposition : « Publier sur le web »**

- On publie une note, avec ses sous-pages si on veut, ou un dossier entier.
  On obtient une adresse publique en lecture seule :
  `https://savoire.app/p/<nom>`. Un domaine à soi viendra plus tard.
- La page est **rendue côté serveur**, en HTML simple : rapide, lisible sans
  JavaScript, référençable. Un petit service Node réutilise le code
  TypeScript de l'appli (comme le pair indexeur) pour rendre callouts, bases,
  formules et images.
- **Navigation** : un menu des pages publiées. Un lien vers une page non
  publiée devient du simple texte : rien ne fuit.
- **Réglages** : référencement par les moteurs (oui ou non), bouton
  « Dupliquer dans mon vault », date de fin, mot de passe (plus tard).
- **Droits** : seuls le propriétaire et les éditeurs publient. Dépublier est
  immédiat.
- **Vault chiffré** : publier revient à donner la page en clair au serveur.
  Un avertissement le dit avant.

Questions :

- **Q16.** **En direct** (chaque modification apparaît, comme Notion) ou

  direct, avec une option pour figer.
- **Q17.** Quelle unité : une page et ses sous-pages, ou un dossier ?
- **Q18.** Référencement par les moteurs activé par défaut ?

## 6. Modules embarquables, comme Microsoft Loop

**État du code, vérifié cette nuit.** `@[[Note.md]]` affiche la note dans un
cadre, modifiable et collaborative. **Cela marche dans l'appli web** (capture
`p57-module.png`). Mais :

- cela ne marche **que dans Savoire** : le cadre utilise la session de
  l'appli ;
- chaque module charge l'appli entière : c'est lourd ;
- un reste de l'ancienne connexion appelle `/api/v1/auth/refresh`, qui
  n'existe plus depuis Zitadel. C'est du code mort ;
- l'appli de bureau n'est pas testée ;
- rien ne dit qu'une note **est** un module : toute note peut s'intégrer.

**Proposition**

1. **Déclarer** : une propriété `module: true`, ou un interrupteur « Module »
   dans le panneau des propriétés. Le module reçoit un identifiant stable et
   ses propres réglages d'accès.
2. **Une page légère** `https://savoire.app/m/<id>` : l'éditeur et la
   synchro, sans le reste de l'appli. Elle est faite pour un cadre (iframe),
   et sa hauteur suit son contenu (le message existe déjà).
3. **Trois niveaux d'accès** en dehors de Savoire :
   - **lecture publique**, pour un site web : simple, à faire en premier ;
   - **modification par une personne connectée** : la connexion se fait dans
     une fenêtre à part. Les navigateurs bloquent les cookies dans un cadre
     venu d'un autre site ; le jeton reste donc en mémoire du cadre ;
   - **Teams** : une « application d'onglet » Teams, avec l'authentification
     unique de Microsoft (Entra) échangée contre un jeton Zitadel. C'est un
     vrai chantier, à faire après les deux autres.
4. **Intégration automatique** : une adresse oEmbed, pour que Notion,
   WordPress ou Slack affichent un module à partir de son seul lien. Et un
   petit script `<savoire-module id="…">` pour les sites.
5. **Sécurité** : liste des sites autorisés à intégrer chaque module.

Questions :

- **Q19.** Qu'est-ce qui peut être un module : une note entière seulement, ou
  aussi un passage (comme les composants Loop) ?
- **Q20.** Priorité : lecture sur un site web d'abord, puis modification,
  puis Teams ?
- **Q21.** Par défaut, un module intégré ailleurs est-il en lecture seule ?

## 7. Base documentaire existante (Word, PDF, sites)

**Aujourd'hui**

- L'appli de bureau ouvre n'importe quel dossier. Tous les fichiers
  apparaissent. Seuls le Markdown et les types des plugins s'éditent.
- Word, Excel et PowerPoint : le plugin Office est un **lien** vers la
  version en ligne. Savoire ne lit pas leur texte.
- L'index lit les notes, et les types CRDT par un Markdown dérivé. **Il ne
  lit pas le texte des PDF ni des Word.** Une recherche ne les trouve donc pas.

Savoire peut donc **ranger** une base existante, mais pas encore la
**connaître**.

**Proposition : des « extracteurs » fournis par des plugins**

- L'API gagne `api.indexing.registerExtractor({ extensions, extraire(octets) })`.
  L'extracteur rend le texte, un titre, des sections, éventuellement des
  propriétés.
- Le **même code** tourne partout où l'index tourne : sur le poste (appli de
  bureau), sur le pair indexeur du serveur, et dans le navigateur. Le résultat
  est gardé selon le contenu du fichier : on n'extrait qu'une fois.
- Le texte entre dans la recherche plein texte, les extraits, et plus tard les
  agents IA.
- **Formats faciles, sans dépendance** : DOCX, PPTX, XLSX et ODT (ce sont des
  archives de XML), HTML, TXT, CSV.
- **PDF** : il faut une bibliothèque, pdf.js (Mozilla, Apache-2.0). C'est une
  dépendance à valider (Q22).
- **OCR** des scans : plus tard (tesseract.js, Apache-2.0).
- **Sites web** : une « source web », c'est-à-dire une liste d'adresses ou un
  sitemap, relue régulièrement **par le serveur** (le navigateur n'a pas le
  droit d'aller lire un autre site). Chaque page devient un document en
  lecture seule, indexé.
- **Aperçu** : le PDF s'affiche déjà avec le lecteur du navigateur, sans
  dépendance. Le DOCX aurait un aperçu HTML simple.
- **Connecteurs** SharePoint, OneDrive, Google Drive (synchro de dossiers) :
  le « deuxième niveau » dont tu parlais le 07/10. Plus tard.

Questions :

- **Q22.** pdf.js : d'accord pour cette dépendance ?
